## 5. Application code expectations

### Postgres

You receive a ready-made Postgres connection string via `ConnectionStrings__DefaultConnection` (bound by this app's source-generated config accessor) — the operator builds it (pointing at CNPG's failover-aware `-rw` service, `connect_timeout=5` already set) and injects it as a secret. You never assemble or tune the DSN itself. CNPG failover is real enough to plan for: measured on this cluster, **~40–50s** of write unavailability for a worker-node loss, more (~60s) for a control-plane node.

This app currently calls `opts.UseNpgsql(cs)` with no retry policy ([`DatabaseConfiguration.cs`](../../src/WebApi/Configurations/DatabaseConfiguration.cs)) — recommend adding `.EnableRetryOnFailure()` so EF Core retries transient failures automatically during a failover/rollout, instead of the request just failing. Not strictly blocking for a first test deploy, but a pod restart storm during a routine database rollout is the kind of thing this would quietly fix.

Migrations run automatically at startup (`dbContext.Database.Migrate()`, unconditional) — that's already reflected in `migrations: startup` / `canMigrate: true` above, no change needed.

### OpenTelemetry

Already enabled in code and requires the explicit env vars set in §4 above (`Telemetry__CollectorEndpoint`, `Telemetry__ServiceName`) — **not** the platform's auto-injected `OTEL_*` vars, which this app does not read. Do not remove those two `env[]` entries from the manifest thinking the platform handles it automatically; for this app specifically, it doesn't.

### Node loss, generally

Stateless replicas with `replicaCount: 1` (the operator's likely default for a first test deploy) do **not** get rescheduled immediately when their node goes unreachable — expect no healthy pod for up to ~5 minutes (Kubernetes' default pod-eviction grace period) until the platform evicts and reschedules it. Not something to fix in this repo; flagging so it's not mistaken for a bug during test verification.

```bash
#!/usr/bin/env bash
# Copy each given service's image tag from the test manifest onto
# production. Never rebuilds — only moves already-tested tags forward.
#   copy-test-tags-to-production.sh SERVICE [SERVICE...]
set -euo pipefail

services=("$@")
if [[ ${#services[@]} -eq 0 ]]; then
  echo "usage: $0 SERVICE [SERVICE...]" >&2
  exit 1
fi

here=$(cd "$(dirname "$0")" && pwd)
pin=$here/pin-image-tag.sh
test_file=deploy/mimir/services.test.yaml
prod_file=deploy/mimir/services.prod.yaml

git config user.name github-actions[bot]
git config user.email github-actions[bot]@users.noreply.github.com

for service in "${services[@]}"; do
  tag=$(bash "$pin" --print "$test_file" "$service")
  bash "$pin" "$prod_file" "$service" "$tag"
done

git add "$prod_file"
if git diff --staged --quiet; then
  echo "production already matches test"
  exit 0
fi
git commit -m "chore: pin production to current test tags [skip ci]"
git push origin HEAD:main
```
